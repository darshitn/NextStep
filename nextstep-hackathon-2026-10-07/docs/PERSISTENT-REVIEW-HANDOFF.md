## Design to implement

This is an additive field in the existing owner-scoped, versioned JSON goal state; it needs no SQL migration/new table. Preserve the current RLS/JWT client and optimistic compare-and-set update. There is no arbitrary goal expansion or AI call in recall saving.

1. Update contract first: `POST /api/goal/learning/recall` with strict payload `{ expectedVersion, missionId, attemptId, attemptText, confidence }`. `attemptId` is a client-generated UUID reused for retry of the SAME payload. `attemptText` is trimmed 1–2000 chars; reject whitespace-only. Confidence integer 1–5 with clear self-rating labels. Server validates mission ID and allows only recorded completed missions or the next eligible incomplete mission (same eligibility boundary as guidance). Unknown ID 404, future incomplete 422, absent goal 404, validation 422, transient DB 503, version conflict 409.
2. Store server-authoritative `{ attemptId, attemptText, confidence, savedAt, nextReviewDate }` in `state.learning[missionId].recallHistory`, retaining latest **20** records chronologically. Missing field on old goals means empty history. Server receipt determines savedAt; nextReviewDate is an Asia/Kolkata calendar date, not a UTC string slice. Mapping of confidence 1/2/3/4/5 to 1/2/3/7/14 calendar days is an explicitly labelled product heuristic, not a validated memory algorithm. Do not accept timestamps or due dates from the client.
3. Duplicate retry: after owner-scoped load and eligibility, if the same retained attemptId and same normalized text/confidence already exists, return the current goal plus that saved record without changing version/history even if expectedVersion is stale. A reused ID with different payload returns a clear 409 conflict, never replaces the original. A new ID uses expectedVersion and database CAS. If CAS loses a race, re-read once to distinguish an already-saved identical attempt from a true conflict; never blindly retry mutation. Keep the latest-20 replay window explicit. Preserve every unrelated goal/learning field, blockers, guidance, assessment, schedule, completions and XP. Do not mark ready or dismiss blockers automatically.
4. Return `{ data: { goal, recallAttempt } }` using the existing derived goal shape. Old load/save/recovery/complete/check operations must retain recallHistory. Add live adapter, apiService wrapper and synthetic fixture with matching behavior/source conventions. Authentication expiry handling remains consistent with existing protected requests.
5. Recall UI: keep recall-before-reflection workflow, add self-rated confidence and an explicit **Save review** action. Show saving/error/retry/success, saved timestamp, next due date and saved history for that mission. Save failure/409 preserves draft and confidence; conflict offers explicit refresh, then an intentional retry. Ambiguous network timeout retry reuses attemptId/payload so it cannot duplicate history. Editing a previously failed payload creates a new request ID. Reset saved/dirty state only on actual save success. Do not clear a newer draft if input changes while a save is in flight; either disable edits while saving or check exact submitted snapshot. Disable duplicate submits and conflicting close/navigation actions while saving.
6. A saved review survives reload/sign-out because it is returned in the goal state; unsaved text remains clearly labelled session-only. Unsaved draft close guard must still work. Mission switching preserves isolated text/confidence/request IDs, with no stale success/error/history leaking across missions. On successful save update canonical Dashboard goal state; active recall panel derives newest mission history from that state rather than stale selected-item copies.
7. Review scheduling: for missions with saved reviews, due today/overdue become recall suggestions; a future due date suppresses the old hint/age-only repeated suggestion. Never hide an unresolved blocker just because its next review is later. Keep explicit dismissed-note semantics; do not erase or silently un-dismiss existing blockers. Exclude unknown/future incomplete missions. Keep existing no-review-history behavior backward compatible. Show next due dates and make a previously reviewed completed mission accessible via notes/history even when no longer due (do not strand its saved attempts after it leaves the queue). Today review context/nav should use canonical updated counts.
8. Export includes bounded saved review history and due dates, never auth/session data. Notes library should expose recall attempts to search or provide an obvious saved-review history entry point. Existing completion outcome statistics stay unchanged; do not label confidence as mastery or count reviews as mission completions/focus time. Disclose latest-20 retention and heuristic intervals in normal student language.
