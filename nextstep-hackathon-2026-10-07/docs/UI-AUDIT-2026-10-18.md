## Main findings

### U1 — High: Proof buries the useful interaction

At 1440px the page is about 3,590px tall; at 390px about 7,174px. A long lesson, worked example, reference code, pitfalls and knowledge check precede the interactive trace. The main reason to use Proof is far below the initial screen. Multiple similarly framed boxes make reading, predicting, tracing and saving feel like one continuous form.

Desired correction: a coherent Learn / Trace / Reflect studio. Give trace-first access and persistent local lesson controls; keep reading/reference material in deliberate panels or steps. Desktop: code and state/prediction side by side. Mobile: input/state, current prediction and feedback in reading order, with code available on demand. Preserve all lesson content, reference reveal semantics, draft identities and server verification.

### U2 — High: Practice is an unbounded expanded feed

All 120 entries are expanded simultaneously. At 1440px document height is about 24,629px; at 390px about 45,037px; at 320px about 51,579px. There are 240 repeated buttons in the list. Search exists, but browsing overwhelms the student and makes actions visually repetitive.

Desired correction: compact rows/cards with title, topic, difficulty and recorded outcome; expand details when selected. Paginate 15–20 results, keep filters/count/navigation coherent, and retain full access to all 120 items. A selected deep-linked problem must still be locatable. No backend pagination or virtualization library is necessary at this size.

### U3 — High: Atlas is called a map but displays a card grid

`AtlasView.jsx` maps all topics into a two-column grid of detailed cards. Relationships appear as prerequisite prose rather than connected paths. At 390px, all 12 cards precede the inspector, so selected-topic details are far away. The recommendation itself keeps a side-by-side layout at mobile widths and compresses the long title into a narrow column. This wraps into a tall block before the path begins.

Desired correction: compact prerequisite stages with clear recommended/current states, honest recorded progress, and visible relationships or a grouped path. If displaying a true DAG, derive edges from actual catalog prerequisites. On mobile, inspect a topic immediately below its selection or in an accessible detail sheet. Preserve an accessible linear alternative. Do not promise a graph if only cards are implemented.

### U4 — High: mobile navigation dominates the first screen

The seven-item navigation becomes a four-row card before content. In the inspected mobile screenshot it occupies roughly 200px plus surrounding space. The 320px Practice viewport ends before the first problem appears. Desktop card navigation is workable, but mobile needs a smaller shell.

Desired correction: primary mobile navigation plus a labelled More menu, or a compact accessible menu with current location. Keep all destinations discoverable, focus/keyboard behavior correct and deep links compatible. Do not force seven items into unreadable tiny tabs.

### U5 — Medium: competing learning systems and unexplained jargon

Today leads with 12-mission starter progress and a separate Atlas/Proof recommendation in a side rail. Atlas and Roadmap both look like curriculum navigation. New onboarding still describes the older six-hour starter without explaining the larger library. Long technical headings and repeated "invariant", "authoritative", "curriculum" labels increase reading effort before practice.

Desired correction: explain which plan/progress a student is viewing, expose one primary next activity and retain the starter as clearly labelled compatible content. Do not relabel starter 12/12 as course 12/48 or merge independent completion systems. Shorten display chrome and use progressive explanation. Coordinate actual curriculum prose changes with the collaborator.

### U6 — Medium: visual hierarchy is mostly repeated borders and small text

The implementation is functional and has coherent colors, but almost every chunk uses similar bordered surfaces, rounded boxes, badges and 12–14px text. Code and lesson reading compete with metadata. There is little emphasis on the actual manipulation/decision. Raw backticks appear in instructional prose because Markdown-like source strings are rendered as plain text.

Desired correction: a small consistent spacing/type system, fewer competing card containers, 14–16px lesson reading text, restrained borders and clear primary actions. Use safe inline formatting for code-like text or display plain text cleanly; do not introduce unsafe HTML rendering or a large Markdown dependency. Motion should communicate state transitions, respect reduced motion and not delay access.

### U7 — Test/preview follow-ups

- Repair the broken Atlas harness without reintroducing answer keys. Use known semantic answer labels or test-only authoritative data in the Node test process, not public client state; keep assertions about the student-safe catalog.
- Standard synthetic preview still binds `host: true`; source correction to loopback remains outstanding. This audit ran a loopback-only ignored copy.
- The CDP isolation harness reuses a browser profile and has no true independence between reruns. Prefer fresh temporary test profiles/contexts and bounded cleanup of only owned processes. Do not kill user Chrome/Node processes.
- Appearance/focus styles can look like more than one selected nav item in still images. Keep keyboard focus and current-page selection visually distinguishable without removing focus indicators.
